# Experiment Setup

This repository contains the experimental setup used to evaluate the performance of various ontology frameworks and reasoners on the OWL2Bench benchmark.

## Ontology Generation

The ontology used in the experiments was generated following the instructions provided in the official OWL2Bench repository:

https://github.com/kracr/owl2bench

We selected the OWL 2 RL profile for the benchmark generation, as this profile aligns with the constraints and goals of our proposed knowledge-reasoning framework. The ABox was generated accordingly using the OWL2Bench scripts.

### Seed Selection

We used seed 1 (seed1) for all experiments.
This seed size already produces an ontology large enough to test the limits of most available frameworks and reasoners, while keeping the dataset manageable for repeated testing and tool comparison.

### Additional Class Modification

During validation, we discovered that Query 5 from the OWL2Bench query set could not be evaluated correctly without the presence of the class T20CricketFan.
Since this class is expected in the benchmark queries but not generated by default, we added it manually to the ontology so that Query 5 would function as intended.

## Experiment Execution

All experiment scripts can be found in the test/ directory.

Each script:

* Loads the generated ontology into a specific framework (Protégé, Owlready2, GraphDB, etc.)

* Applies the selected reasoner (Pellet, HermiT, or the internal reasoner where applicable)

* Executes the benchmark queries

### Records:

* Number of answers returned

* Loading time

* Reasoning time

* Query execution time

The outputs are printed to the console and stored in the corresponding results files for later comparison.

## Purpose

These experiments allow us to compare multiple frameworks and reasoners under identical conditions, providing insights into their performance on OWL 2 RL ontologies and supporting the evaluation of our novel object-oriented knowledge-reasoning approach.


# Frameworks Used in the Experiments

This repository includes experiment scripts for Owlready2, RDFlib, and SPARQLWrapper. Each of these tools was selected to evaluate different aspects of ontology handling, reasoning capabilities, and querying performance. Below is a brief description of why each framework was used and how it was integrated into the experiment pipeline.

### Owlready2 (Loading, Reasoning, Querying with Pellet and HermiT)

We included Owlready2 because it provides a Python-native interface for loading OWL ontologies, manipulating them programmatically, and invoking external reasoners. It supports integration with Pellet and HermiT, allowing us to measure the impact of different OWL DL reasoners under a unified Python workflow. Owlready2 internally converts ontologies into a format suitable for these reasoners, executes reasoning, and exposes the inferred ontology back to Python for subsequent querying. This makes it well suited for evaluating both the reasoning performance and the combined reasoning–querying workflow within a Python environment.

### RDFlib (Loading and Querying)

RDFlib was used to evaluate pure RDF-based loading and querying performance without full DL reasoning. Since RDFlib does not support OWL reasoning, we supplied the already inferred graph generated by external reasoners. This allowed us to isolate the cost of loading and graph-pattern query execution using SPARQL on a static inferred dataset. RDFlib is widely used in semantic web applications, and testing it provides a useful baseline for lightweight querying scenarios where DL reasoning is performed offline.

### SPARQLWrapper (Querying via GraphDB)

SPARQLWrapper was used to measure querying performance against a dedicated graph database. In our setup, the library communicates with a GraphDB instance through its SPARQL endpoint, effectively acting as an HTTP API client. This setup tests a real-world deployment scenario: reasoning and inference are performed inside GraphDB, while queries are executed remotely through the SPARQL protocol. Using SPARQLWrapper allows us to evaluate endpoint query latency, transport overhead, and server-side optimization behavior, providing a contrast to local in-memory querying frameworks like RDFlib and Owlready2.
